## 已定位的问题（未在本轮修复）

### R1 — P1：drain 被当成显式 cancel

位置：[lifecycle_stop.py](../../../sandbox_graph/services/lifecycle_stop.py) 第144–177行。

`request_in` 接受并保存 drain/cancel，但 `consume_in` 对两个 policy 都生成 kind=cancel 的事件，没有 drain 分支。探针在原 provider 已提交、仍未知的情况下请求 drain，得到 `stop_reason=explicit_cancel, terminal_intent=cancelled, phase=cancelling`。

影响：选择旧版本排空时，无法保持“原操作在原期限内完成”的约定，生命周期会进入显式取消路径。这是代码行为缺口，不需要真实虚拟机即可修复。对应45.4-C、48.3；先补 ST-06/07 的实际状态与动作断言。

### R2 — P2：cancel 后仍可建立诊断子任务并预留预算

位置：[agent_team.py](../../../sandbox_graph/services/agent_team.py) 第117–131、254–284行。

`request_role` 的两次事务检查 parent/owner/phase，但未检查已持久化的 run stop。探针保持原 parent owner 有效，调用 RunService.cancel 后再 request_role，实际 gate_open=false，却得到一个 pending agent_team job，并新增 child_jobs=1、diagnosis_calls=1、tokens=30、cost=40 等预留。

执行前 `assert_model_network_in` 还有截止检查，所以本证据不证明取消后已发生模型网络调用。已确认的影响是取消后创建不应存在的任务/预算占用，并把准入错误推迟到执行阶段。对应45.4-C/ST-08；需在实际入队/预留事务拒绝新请求，保留旧请求幂等读取及事实提交。

### R3 — P2：父作用域清点漏掉子生命周期 provider

位置：[lifecycle_stop.py](../../../sandbox_graph/services/lifecycle_stop.py) 第81–83行。

jobs/operations 会按 run/group 聚合，但 provider 只匹配与当前 record 完全相同的 lifecycle_id。探针给同一 run 的 work lifecycle 提交一个未知 provider 请求，以合法 run scope record 清点时 providers=[]。

该探针验证 inventory 函数的聚合缺口，没有冒充完整父图集成。ClosureService 另有扫描所有生命周期/provider 的保护，因此不据此断言“最终归档已经漏掉运行中子任务”。需要统一 stop/closure 的归属规则，避免父 stop 投影或证明低估效果。对应45.4-B/D、ST-03/13。

### R4 — P1（交付缺口）：真实端到端验收入口仍为占位

位置：[test_end_to_end.py](../../../tests/orchestration/e2e/test_end_to_end.py) 第51–57行。

`test_real_dual_group_end_to_end` 在缺环境时 skip，但函数体是 `raise NotImplementedError`。设置 SANDBOX_GRAPH_TEST_PRODUCT_ENV 只会取消 skip，不能得到可运行验收。因此该项同时缺测试实现和真实环境，不能归类为纯环境阻塞。对应14.2及环境适配10.2–10.4。

### R5 — P1（集成缺口）：当前没有包含两边功能的统一验收版本

生命周期实现未提交/合入主区，主区另有资源观测合同与未提交条件配置。当前绿色测试只覆盖生命周期工作树快照。发布前需保留双方改动、形成可复现集成版本并验收；不能假设用户重新 clone 已包含这些代码。本次没有合并或推送。
