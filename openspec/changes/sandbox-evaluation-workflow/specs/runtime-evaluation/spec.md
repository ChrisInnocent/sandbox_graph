# Spec Delta

## Purpose

为沙箱运行时选型定义基础功能及其性能的场景目录、指标分类、条件矩阵与跨方案对齐规则，优先验证实际能力和正确结果，再比较可解释的性能数据，并将补充专项作为低优先级需求保留，避免测试范围无界扩张。

## ADDED Requirements

### Requirement: RT-01 基础评估优先级

系统 SHALL 优先评估 RT-02 的十类基础场景，按适用能力先验证功能，再评价基础功能性能。RT-03 的六类补充场景 SHALL 作为低优先级扩展保留，未经明确纳入当前计划，不得默认执行或成为基础交付的完成门槛。

#### Scenario: 生成首阶段计划
- **WHEN** 用户要求进行基础沙箱选型评估
- **THEN** 计划覆盖十类基础场景的能力核验及适用测试，并将六类补充场景标为低优先级、未纳入本轮

#### Scenario: 扩展未测试
- **WHEN** 某候选只完成基础范围而未进行长期运行或故障恢复专项
- **THEN** 报告可在基础范围内形成结论，同时明确扩展未评估，不能推导长期稳定性或故障恢复能力

### Requirement: RT-02 十类基础场景目录与指标分配

系统 SHALL 维护以下场景表，并按场景采集适用的主要及特有指标。操作类场景共同记录请求数、成功数、失败、超时、拒绝和相关资源开销；具体完成事件、档位及阈值在逐场景测试合同中明确。缺失必需观测时不得将相应指标报告为已验证。

#### Scenario: 审核基础场景覆盖
- **WHEN** 系统准备基础选型计划或报告
- **THEN** 以下十类场景均具有明确的能力及计划状态，已选择的场景具有适用指标和证据入口

| ID | 基础场景 | 主要指标 | 特有指标或结果验证 |
|---|---|---|---|
| B01 | 从模板／快照创建沙箱 | 请求到可执行时延、成功创建吞吐、整批完成时间 | 首次命令完成时延、模板／快照读取量、创建资源峰值；来源类型分别记录 |
| B02 | 从镜像创建沙箱 | 请求到可执行总时延、成功创建吞吐 | 拉取、解包、转换／构建、启动阶段耗时，下载量、磁盘占用 |
| B03 | 沙箱暂停 | 暂停完成时延、成功暂停吞吐、业务停止窗口 | 暂停后 CPU／内存／磁盘占用、资源释放时间、保存状态 |
| B04 | 沙箱恢复 | 恢复到可执行时延、成功恢复吞吐 | 首次任务完成时间、恢复期资源峰值、状态连续性 |
| B05 | 沙箱克隆 | 单个子实例就绪时延、整批就绪时间、成功克隆吞吐 | 子实例增量开销、源实例影响、状态继承及子实例独立性 |
| B06 | 沙箱删除 | 删除接口时延、实际终止时延、成功删除吞吐 | 资源实际释放时间、残留进程／挂载／网络资源 |
| B07 | 沙箱命令执行 | 提交到开始执行时延、首输出时延、完成时延、成功命令吞吐 | 输出传输速率、退出状态、输出正确性、执行链路开销 |
| B08 | 沙箱快照 | 快照完成时延、成功快照吞吐、业务暂停窗口 | 逻辑大小、实际新增存储量、读写量、发布耗时、可恢复性 |
| B09 | 沙箱底噪 | 无业务时 CPU、内存、磁盘及网络活动 | 平台固定开销、实例增量开销、周期性抖动、观察窗口内资源变化 |
| B10 | 单节点沙箱部署密度 | 约定条件下可持续承载的实例数 | 不同密度下操作时延、有效业务吞吐、失败率、OOM、资源余量 |

### Requirement: RT-03 低优先级扩展目录

系统 SHALL 保留以下六类扩展及其评估目的和候选指标。目录保留不等于当前要求执行；扩展被纳入计划后才细化工作负载、条件和验收标准。基础场景的必要正确性检查不因扩展降级而被省略。

#### Scenario: 查询后续扩展需求
- **WHEN** 用户查看基础评估之后可以补充的测试
- **THEN** 系统展示下表并明确其优先级低于基础场景，不将未完成扩展列为首阶段失败

| ID | 低优先级扩展 | 评估目的 | 候选指标 |
|---|---|---|---|
| E01 | 沙箱内负载执行性能 | 区分命令接口开销与实际计算、内存、磁盘、网络能力 | 固定任务完成时间、CPU／内存性能、磁盘 IOPS／带宽／时延、网络带宽／时延 |
| E02 | 快照回滚／状态重置 | 评价将当前实例恢复到旧状态的行为 | 回滚时延、业务中断窗口、回滚后首次任务时延、状态正确性 |
| E03 | 混合生命周期与长期运行 | 观察反复创建删除、混合操作、积压和长期退化 | 持续成功吞吐、尾时延变化、资源增长斜率、残留量、性能恢复时间 |
| E04 | 资源弹性与压力下运行 | 观察资源紧张或活跃率变化时的有效工作 | 准入率、排队时间、回收／重新分配时延、业务吞吐、OOM和任务丢失 |
| E05 | 共置负载干扰 | 观察一个沙箱负载对其他沙箱性能的影响 | 受影响任务时延和吞吐变化、资源分配偏差 |
| E06 | 故障后恢复性能 | 观察控制组件或节点异常后的服务恢复代价 | 不可用时长、恢复时间、任务丢失／重复、积压清空时间 |

#### Scenario: 基础命令执行验证输出
- **WHEN** B07 验证固定命令的退出状态和输出
- **THEN** 该验证仍属于基础功能；不因 E01 未启用而跳过，也不自动扩展成完整计算和 I/O 基准

### Requirement: RT-04 场景条件指标分离

系统 SHALL 分别描述操作场景、实验条件和观测指标，允许同一场景在不同条件下执行并采集不同指标。测试实例 SHALL 明确三者及合同版本，不将指标名称或条件档位当作未定义的新操作能力。

#### Scenario: 在已有实例下测试创建
- **WHEN** 计划在既定数量的存量沙箱上以某并发度创建新实例
- **THEN** 系统分别记录创建场景、已有实例数与操作并发条件，以及就绪时延和成功吞吐等指标

### Requirement: RT-05 六类统一指标

系统 SHALL 按下表维护指标分类、单位、观测范围、计算方式及适用场景。共用分类不要求所有指标在每个场景或每轮执行；不适用或未采集项须有明确状态，不可填零冒充测量值。

#### Scenario: 生成场景指标清单
- **WHEN** 系统将场景转换为可执行测试合同
- **THEN** 按下表选择适用指标，说明必要证据及计算规则，并将扩展专属指标限制在已选择范围内

| 指标类型 | 内容 |
|---|---|
| 时间 | 逐请求时延、P50／P95／P99、批次完成时间、必要阶段耗时 |
| 吞吐 | 实际发起速率、接纳速率、正确完成速率；有期限要求时另报期限内完成速率 |
| 可靠性与正确性 | 失败、超时、拒绝、重试、状态恢复正确性、输出正确性 |
| 资源与效率 | 按节点角色和组件报告 CPU 时间、利用率，内存占用，磁盘容量与 I/O、网络流量；分别记录峰值和稳态窗口统计，以及单位成功操作资源消耗 |
| 容量与稳定性 | 可持续实例数、饱和点、排队增长、资源变化及性能退化；长期指标按已选择观察窗口评价 |
| 状态与产物 | 快照大小、实际新增存储量、资源释放量、残留资源、恢复后状态一致性 |

### Requirement: RT-06 条件参数矩阵

系统 SHALL 按下表描述适用条件轴，显式记录选取的组合、未覆盖范围和采样计划。系统不得默认执行所有条件的笛卡尔积；基础评估先使用已确认的有限档位，参数数值和实验规模未经确认不得作为固定要求。

#### Scenario: 展开测试矩阵
- **WHEN** 为同一场景设计不同条件下的实验
- **THEN** 系统从下表选择适用轴并形成可检查的有限组合，说明固定变量、变化变量和所需重复轮次

| 条件轴 | 需要描述的内容 |
|---|---|
| 已有实例数 N | 操作前存量实例数及状态，试验中实例数是否变化 |
| 操作并发数 C | 同时尚未完成的操作数、限额及实际观测值 |
| 请求到达率 λ | 计划与实际发起速率、到达模式以及无法发起的请求 |
| 实例状态与负载 | 空闲、活跃或暂停，负载类型及活跃比例 |
| 沙箱规格 | 规格标识、请求的 vCPU／内存／磁盘及明确单位、实际生效资源配置；例如 2v2G、2v4G，具体档位与 G 的含义待确认 |
| 数据状态 | 镜像／快照大小、脏页量、工作集、快照链深度 |
| 缓存与预备状态 | 数据位置、各层冷热、预热／预取、预创建池 |
| 部署与时间条件 | 单机或集群、同节点或跨节点、观察时长及重复轮次 |

### Requirement: RT-07 跨方案外部语义对齐

系统 SHALL 先定义用户可观察的输入状态、操作、完成事件、正确性及输出，再结合对应版本源码与实际验证映射各方案的接口和内部阶段。内部阶段用于诊断，不要求所有产品有相同组件；不能仅按相同 API 名称认定操作等价。

#### Scenario: 同名恢复接口行为不同
- **WHEN** 一个方案恢复同一实例状态，另一个方案从磁盘重新启动新实例
- **THEN** 系统记录身份和状态语义差异，不能将两者作为未加说明的同一恢复能力排名

#### Scenario: 官方测量口径不一致
- **WHEN** 官方脚本分别测量 API 返回、业务就绪或整个用例耗时
- **THEN** 系统保留其原口径，按统一合同补充测量或标记不可直接比较，不仅重命名指标就声称已经对齐

### Requirement: RT-08 能力支持与测试覆盖分别记录

系统 SHALL 区分原生支持、组合操作实现、明确不支持和尚未验证，并另行记录测试是否执行及结果。官方脚本缺失不能直接认定能力不支持，尚未测量不能记为失败或零耗时。组合实现 SHALL 记录组成操作及完整成本。

#### Scenario: 功能存在但没有官方压测
- **WHEN** 源码及实际功能验证显示某能力存在而官方未提供性能脚本
- **THEN** 系统记录适配和补测需求，不将该能力列为不支持

#### Scenario: 候选明确缺少能力
- **WHEN** 某候选不具备本次所需能力
- **THEN** 报告记录能力缺口及选型影响，不把它混为性能脚本失败，也不静默删除该比较项

### Requirement: RT-09 功能验证先于性能结论

系统 SHALL 对适用场景验证真实状态变化、可执行性或结果正确性；性能采样中的每次操作仍需检查其完成结果。功能验证通过一次不能使后续全部请求自动计为成功，功能失败的计时必须保留但不得作为成功操作时延。

#### Scenario: API 返回成功但沙箱不能执行
- **WHEN** 创建接口返回成功而约定的 Guest 命令或业务就绪验证失败
- **THEN** 系统记录接口结果及功能失败，不计入成功创建吞吐

#### Scenario: 克隆或快照功能验证
- **WHEN** 测试合同要求继承或恢复特定状态
- **THEN** 系统按声明检查状态及克隆独立性，性能结果绑定对应正确性证据

### Requirement: RT-10 计时事件与恢复后有效工作

系统 SHALL 区分接口返回、实际操作完成、可执行和首次有效工作完成等适用事件，分别定义起止位置、时钟和观测方式。创建及恢复不能只凭控制 socket 或进程存在宣称可用，删除不能只凭接口响应宣称资源已释放。

#### Scenario: 恢复完成后仍按需读取数据
- **WHEN** 恢复接口返回后首次任务仍需读取工作集
- **THEN** 系统分别记录恢复到可执行及首次任务完成时间，不将接口完成等同于工作集已全部就绪

#### Scenario: 删除异步回收
- **WHEN** 删除请求已响应而进程或资源尚未释放
- **THEN** 系统分别记录接口时延、终止及释放观测，并按合同判断完成状态

### Requirement: RT-11 逐请求时延与统计可靠性

系统 SHALL 保留逐请求时延、批次完成时间和摊销值的区别，分位数必须由对应口径的样本计算并标明样本数、重复轮次和波动信息。成功时延分布 SHALL 与失败、超时及其他结果共同报告，样本不足时不能把尾部分位数包装成稳定结论。

#### Scenario: 只有批次耗时
- **WHEN** 脚本只记录整批耗时和并发数
- **THEN** 系统可报告批次耗时及摊销值，但不能据此生成逐请求 P95 或宣称摊销值等于逐请求平均时延

#### Scenario: 成功样本有选择性
- **WHEN** 部分操作超时而成功请求较快
- **THEN** 系统同时展示超时数量及处理规则，不仅引用成功分位数宣称整体性能良好

### Requirement: RT-12 正确完成吞吐

系统 SHALL 分别记录计划发起、实际发起、接纳和正确完成的数量及速率，说明各自时间窗口；有完成期限时另报期限内正确完成量。业务提交或准入成功不能替代业务完成，重试和迟到完成应按合同单独归属。

#### Scenario: 请求大量被接纳但完成缓慢
- **WHEN** 控制面接受大量创建请求而只有部分实例就绪
- **THEN** 报告分别展示接纳和成功就绪吞吐，不用接纳速率代表创建完成能力

### Requirement: RT-13 资源分层与增量开销

系统 SHALL 区分宿主整体、平台常驻组件、单沙箱运行时与 Guest 内负载的资源观测，说明 CPU、内存、I/O 的口径和窗口，避免跨层重复相加。固定开销与实例增量开销分别报告；单位成功操作开销必须明确分子是否包含失败及共享服务成本。

#### Scenario: 多层内存观测重叠
- **WHEN** 同时采集宿主、进程或 cgroup 和 Guest 内存
- **THEN** 系统保留各层口径，不直接相加为总内存；共享页和不同内存指标不能混作同一计量

#### Scenario: 估计单实例底噪
- **WHEN** 比较不同实例数量下的资源开销
- **THEN** 系统保留基线与增量关系，不仅以全机资源除以实例数推导单实例固定成本

### Requirement: RT-14 密度并发与到达率独立

系统 SHALL 分别建模已有实例数 N、操作并发数 C 和请求到达率 λ。固定并发与固定到达率 SHALL 标明负载模型及实际实现值，不能因系统变慢使实际发起速率下降而仍声称维持目标速率，也不能把存量实例数当作请求并发。

#### Scenario: 存量密度下并发创建
- **WHEN** 已有 N 个沙箱时以 C 并发执行创建
- **THEN** 系统分别记录存量状态、实际操作并发及新增实例数，声明测量期间密度是否保持不变

#### Scenario: 负载发生器未达到目标速率
- **WHEN** 计划到达率高于实际发起速率
- **THEN** 系统报告差额及已知原因，不能将未实际施加的压力下结果作为目标速率测试通过

### Requirement: RT-15 单节点密度的条件化结论

系统 SHALL 同时支持将实例数作为测试条件，以及在明确时延、正确完成率、资源约束和观察窗口下求得可持续承载量。空闲实例容量与活跃工作容量 SHALL 分别报告；不能通过忽略拒绝、Guest 失败、OOM或工作丢失提高密度结论。

#### Scenario: 空闲实例多但活跃工作失败
- **WHEN** 节点能够创建大量空闲实例，而对应活跃负载出现失败
- **THEN** 报告区分空闲密度与活跃密度，不把前者当作后者的容量证明

### Requirement: RT-16 数据来源缓存及准备成本

系统 SHALL 区分模板与快照来源，记录其实际状态内容、数据位置及缓存／预备条件。从镜像创建 SHALL 区分完整准备路径与已准备路径，明确拉取、转换或模板构建成本是否计入，不能遗漏或重复计入一次性成本。

#### Scenario: 必须先把镜像转换为模板
- **WHEN** 某方案不能直接从镜像启动而需预先生成模板
- **THEN** 系统报告完整路径的转换及启动成本，并可另报模板已准备后的创建性能，不能将两种结果混用

#### Scenario: 缓存状态不一致
- **WHEN** 一个方案使用预热本地数据而另一个从远端首次读取
- **THEN** 系统记录差异并按合同分组或补测，不将两者直接标成同等冷启动条件

### Requirement: RT-17 生命周期状态和产物语义

系统 SHALL 为暂停、恢复、克隆、快照及删除记录实例身份连续性、内存与磁盘状态、资源保留或释放行为。快照 SHALL 区分生成、发布、可恢复等适用完成点及逻辑大小、实际新增存储量，不能仅按接口名称或返回成功认定等价。

#### Scenario: 暂停仅停止执行但保留内存
- **WHEN** 某方案暂停后保留运行状态与内存资源
- **THEN** 系统报告停止执行时间和保留资源，不把该结果直接解释为资源回收完成

#### Scenario: 快照返回标识但尚不可恢复
- **WHEN** 快照接口返回标识而所需数据尚未完整可用
- **THEN** 系统分别记录返回和可恢复状态，按测试合同完成恢复验证后才给出对应成功结论

### Requirement: RT-18 测试设计与执行责任

系统 SHALL 将源码与接口语义分析、确定性测量和人工决策分工记录，模型分析必须关联对应候选版本的源码或文档证据并由实际验证补强。指标计算、条件展开和已明确断言由脚本执行，必要口径和选型取舍由人工明确。

#### Scenario: 生成候选方案测试适配
- **WHEN** 同一基础场景需要适配不同沙箱
- **THEN** 系统按下表形成证据及责任记录，未经验证的模型推断保持待验证，不进入已确认能力或性能结论

| 工作 | 脚本职责 | 模型职责 | 人工确认条件 |
|---|---|---|---|
| 场景和条件计划 | 校验结构、依赖、有限档位及覆盖情况 | 将需求拆成场景与条件草案 | 新增范围、档位、规模或优先级尚未明确 |
| 源码与语义分析 | 定位版本与入口，执行可验证检查 | 分析调用路径、状态语义、阶段和证据缺口 | 多种语义会改变比较目标且无法从既有要求决定 |
| 功能验证 | 执行断言、保留全部结果及状态证据 | 解释未覆盖异常 | 需要改变功能合同或授权范围 |
| 性能采集 | 按计划发压、记录逐请求及资源观测 | 诊断异常、提出补测建议 | 改变负载模型、资源档位或测试规模 |
| 分析与结论输入 | 统计、对齐检查、证据索引 | 解释差异、列明假设和适用边界 | 阈值、权重或业务取舍未确定 |

### Requirement: RT-19 沙箱规格作为独立实验条件

系统 SHALL 将沙箱规格作为独立条件轴，关联测试计划、请求、实例、结果和运行快照，记录规格标识、vCPU 数、内存及磁盘容量的明确单位、请求值与实际生效值。规格、资源预留或上限、实测占用 SHALL 分别表达；跨方案按规格及有效资源策略分组比较。平台最大／无约束配置不得静默解除测试指定的单沙箱规格约束；不支持、无法核实或生效不符须明确记录。

#### Scenario: 同一场景采用不同沙箱规格
- **WHEN** 用户选择 2v2G 与 2v4G 两个规格测试创建性能
- **THEN** 计划先明确 G 的单位并保留规范化容量，分别关联两个规格下的 N、C、负载及结果，不将不同规格样本混成一个未分组的时延或密度结论

#### Scenario: 请求规格与生效规格不同
- **WHEN** 请求的资源配置被平台默认值覆盖、候选不支持该规格或无法读取实际生效值
- **THEN** 系统保留请求和观测证据，分别标记不符、不支持或未验证，不静默替换规格后声称完成同规格比较

#### Scenario: 规格变化后重入测试
- **WHEN** 测试需求从一个规格改为另一个规格并恢复工作流
- **THEN** 系统创建新的条件版本并重新判定受影响结果的有效性，保留旧结果；模板或快照自带规格时核实其与目标规格是否兼容

### Requirement: RT-20 基础场景的稳态资源观测

系统 SHALL 在适用基础场景中同时支持峰值与稳态资源分析，区分生命周期过渡、空闲稳态和约定负载下的稳态。测试合同 SHALL 定义预热／排除区间、稳态判据、采样间隔、观察时长与等待上限，按实际时间窗口计算资源均值、分位数、波动或趋势等适用统计并保留原始序列。未达到判据或采集缺失不得宣称稳态已验证。基础稳态观测属于首阶段，不以低优先级长期运行场景为前提。

#### Scenario: 创建后进入空闲稳态
- **WHEN** 一批指定规格的沙箱创建完成并保留运行
- **THEN** 系统分别报告创建阶段峰值与满足判据后的空闲稳态资源，标明窗口、实例数和规格，不用启动峰值代替稳态占用

#### Scenario: 固定负载下观察稳态
- **WHEN** 测试合同要求在指定实例数与负载下持续观察资源
- **THEN** 系统记录实际负载和实例数，脚本按合同判断窗口并计算统计，注明 CPU 利用率分母、内存口径以及 I/O 与网络的速率或累计量，不将空闲结果当作负载稳态结果

#### Scenario: 未形成稳态或证据不足
- **WHEN** 等待达到上限仍不满足稳态判据，或样本缺口影响判断
- **THEN** 系统保留完整观测、判定原因与峰值结果，分别标记未达到稳态或无法验证；模型不得自行挑选平坦片段作为已通过证据

### Requirement: RT-21 按节点角色和组件归属分析资源

系统 SHALL 按环境、节点、节点角色、组件及实例建立资源观测归属，覆盖适用的管理节点管理进程、数据节点管理进程、数据节点沙箱运行时进程及其他必要组件。采集对象可为进程、容器或 cgroup，须记录身份、口径、时间与父子关系，保留节点整体、组件总量和适用单实例统计。共享服务、单节点角色共置及宿主／Guest 重叠统计 SHALL 明确边界，避免重复相加或无依据分摊。

#### Scenario: 多角色组件稳态资源报告
- **WHEN** 集群在某规格、实例数和负载条件下完成稳态观测
- **THEN** 报告逐节点区分管理节点管理组件、数据节点管理组件及沙箱进程的峰值与稳态资源，并关联同一实验窗口和原始证据；共享管理开销与单沙箱增量开销分别表达

#### Scenario: 单机共置角色或组件重启
- **WHEN** 同一主机同时承担管理和数据角色，或观测期间组件进程重启
- **THEN** 系统依据实际观测对象去重，并以进程启动身份或等价标识区分重启前后样本；无法归属的资源保留为未知，不从组件合计中静默丢弃

#### Scenario: 确定采集映射与计算职责
- **WHEN** 为候选沙箱建立角色、组件和采集对象映射
- **THEN** 模型依据版本化源码与部署证据提出映射，脚本验证对象并采集、判稳、聚合和检查完整性；口径或阈值无法从既有合同确定时由人工确认，模型解释不替代实测值
