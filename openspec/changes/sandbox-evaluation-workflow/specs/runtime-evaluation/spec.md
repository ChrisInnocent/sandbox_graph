# Spec Delta

## Purpose

为沙箱运行时选型定义基础功能及其性能的场景目录、指标分类、条件矩阵与跨方案对齐规则，优先验证实际能力和正确结果，再比较可解释的性能数据，并将补充专项作为低优先级需求保留，避免测试范围无界扩张。

## ADDED Requirements

### Requirement: RT-01 基础评估优先级

系统 SHALL 优先评估 RT-02 的十类基础场景，按适用能力先验证功能，再评价基础功能性能。RT-03 的六类补充场景 SHALL 作为低优先级扩展保留，未经明确纳入当前计划，不得默认执行或成为基础交付的完成门槛。

#### Scenario: 生成首阶段计划
- **WHEN** 用户要求进行基础沙箱选型评估
- **THEN** 计划覆盖十类基础场景的能力核验及适用测试，并将六类补充场景标为低优先级、未纳入本轮

#### Scenario: 扩展未测试
- **WHEN** 某候选只完成基础范围而未进行长期运行或故障恢复专项
- **THEN** 报告可在基础范围内形成结论，同时明确扩展未评估，不能推导长期稳定性或故障恢复能力

### Requirement: RT-02 十类基础场景目录与指标分配

系统 SHALL 维护以下场景表，并按场景采集适用的主要及特有指标。操作类场景共同记录请求数、成功数、失败、超时、拒绝和相关资源开销；具体完成事件、档位及阈值在逐场景测试合同中明确。缺失必需观测时不得将相应指标报告为已验证。来源产物构建场景见 RT-41，作为独立目录与以下实例操作场景并列，不计入十类基础场景。

#### Scenario: 审核基础场景覆盖
- **WHEN** 系统准备基础选型计划或报告
- **THEN** 以下十类场景均具有明确的能力及计划状态，已选择的场景具有适用指标和证据入口

| ID | 基础场景 | 主要指标 | 特有指标或结果验证 |
|---|---|---|---|
| B01 | 从模板／快照创建沙箱 | 到合同状态的创建时延、成功创建吞吐、整批完成时间；经核验内部耗时单列 | API、可选首次命令完成时延、模板／快照读取量、创建资源峰值；按来源产物 kind 与启动路径分别记录，快照来源区分磁盘与内存 |
| B02 | 从镜像创建沙箱 | 完整准备路径到所选完成点的总时延、对应成功吞吐 | 拉取、解包、转换／构建、启动阶段耗时，下载量、磁盘占用；已准备路径另列 |
| B03 | 沙箱暂停 | 暂停完成时延、成功暂停吞吐、业务停止窗口 | 暂停后 CPU／内存／磁盘占用、资源释放时间、保存状态 |
| B04 | 沙箱恢复 | 恢复到可执行时延、成功恢复吞吐 | 首次任务完成时间、恢复期资源峰值、状态连续性 |
| B05 | 沙箱克隆 | 单个子实例就绪时延、整批就绪时间、成功克隆吞吐 | 子实例增量开销、源实例影响、状态继承及子实例独立性 |
| B06 | 沙箱删除 | 删除接口时延、实际终止时延、成功删除吞吐 | 资源实际释放时间、残留进程／挂载／网络资源 |
| B07 | 沙箱命令执行 | 提交到开始执行时延、首输出时延、完成时延、成功命令吞吐 | 输出传输速率、退出状态、输出正确性、执行链路开销 |
| B08 | 沙箱快照 | 快照完成时延、成功快照吞吐、业务暂停窗口 | 逻辑大小、实际新增存储量、读写量、发布耗时、可恢复性 |
| B09 | 沙箱底噪 | 无业务时基于 PSS 的内存底噪及 CPU、磁盘、网络活动 | 保留原始 PSS，按可核验合同剔除 Guest OS；平台固定开销、实例增量开销与波动 |
| B10 | 单节点沙箱部署密度 | 约定条件下实际拉起、存活及健康实例数，实测规模与资源估算分列 | 同步采集各角色／组件 PSS、累计 CPU 时间、CPU 峰值，按实际存活数量计算适用均值，并记录失败和余量 |

### Requirement: RT-03 低优先级扩展目录

系统 SHALL 保留以下六类扩展及其评估目的和候选指标。目录保留不等于当前要求执行；扩展被纳入计划后才细化工作负载、条件和验收标准。基础场景的必要正确性检查不因扩展降级而被省略。

#### Scenario: 查询后续扩展需求
- **WHEN** 用户查看基础评估之后可以补充的测试
- **THEN** 系统展示下表并明确其优先级低于基础场景，不将未完成扩展列为首阶段失败

| ID | 低优先级扩展 | 评估目的 | 候选指标 |
|---|---|---|---|
| E01 | 沙箱内负载执行性能 | 区分命令接口开销与实际计算、内存、磁盘、网络能力 | 固定任务完成时间、CPU／内存性能、磁盘 IOPS／带宽／时延、网络带宽／时延 |
| E02 | 快照回滚／状态重置 | 评价将当前实例恢复到旧状态的行为 | 回滚时延、业务中断窗口、回滚后首次任务时延、状态正确性 |
| E03 | 混合生命周期与长期运行 | 观察反复创建删除、混合操作、积压和长期退化 | 持续成功吞吐、尾时延变化、资源增长斜率、残留量、性能恢复时间 |
| E04 | 资源弹性与压力下运行 | 观察资源紧张或活跃率变化时的有效工作 | 准入率、排队时间、回收／重新分配时延、业务吞吐、OOM和任务丢失 |
| E05 | 共置负载干扰 | 观察一个沙箱负载对其他沙箱性能的影响 | 受影响任务时延和吞吐变化、资源分配偏差 |
| E06 | 故障后恢复性能 | 观察控制组件或节点异常后的服务恢复代价 | 不可用时长、恢复时间、任务丢失／重复、积压清空时间 |

#### Scenario: 基础命令执行验证输出
- **WHEN** B07 验证固定命令的退出状态和输出
- **THEN** 该验证仍属于基础功能；不因 E01 未启用而跳过，也不自动扩展成完整计算和 I/O 基准

### Requirement: RT-04 场景条件指标分离

系统 SHALL 分别描述操作场景、实验条件和观测指标，允许同一场景在不同条件下执行并采集不同指标。测试实例 SHALL 明确三者及合同版本，不将指标名称或条件档位当作未定义的新操作能力。

#### Scenario: 在已有实例下测试创建
- **WHEN** 计划在既定数量的存量沙箱上以某并发度创建新实例
- **THEN** 系统分别记录创建场景、已有实例数与操作并发条件，以及就绪时延和成功吞吐等指标

### Requirement: RT-05 六类统一指标

系统 SHALL 按下表维护指标分类、单位、观测范围、计算方式及适用场景。共用分类不要求所有指标在每个场景或每轮执行；不适用或未采集项须有明确状态，不可填零冒充测量值。

#### Scenario: 生成场景指标清单
- **WHEN** 系统将场景转换为可执行测试合同
- **THEN** 按下表选择适用指标，说明必要证据及计算规则，并将扩展专属指标限制在已选择范围内

| 指标类型 | 内容 |
|---|---|
| 时间 | 逐请求时延、P50／P95／P99、批次完成时间、必要阶段耗时 |
| 吞吐 | 实际发起速率、接纳速率、正确完成速率；有期限要求时另报期限内完成速率 |
| 可靠性与正确性 | 失败、超时、拒绝、重试、状态恢复正确性、输出正确性 |
| 资源与效率 | 按节点角色和组件报告 CPU 时间、利用率，内存占用，磁盘容量与 I/O、网络流量；分别记录峰值和稳态窗口统计，以及单位成功操作资源消耗 |
| 容量与稳定性 | 可持续实例数、饱和点、排队增长、资源变化及性能退化；长期指标按已选择观察窗口评价 |
| 状态与产物 | 快照大小、实际新增存储量、资源释放量、残留资源、恢复后状态一致性 |

### Requirement: RT-06 条件参数矩阵

系统 SHALL 按下表描述适用条件轴，显式记录选取的组合、未覆盖范围和采样计划。系统不得默认执行所有条件的笛卡尔积；基础评估先使用已确认的有限档位，参数数值和实验规模未经确认不得作为固定要求。

#### Scenario: 展开测试矩阵
- **WHEN** 为同一场景设计不同条件下的实验
- **THEN** 系统从下表选择适用轴并形成可检查的有限组合，说明固定变量、变化变量和所需重复轮次

| 条件轴 | 需要描述的内容 |
|---|---|
| 已有实例数 N | 操作前存量实例数及状态，试验中实例数是否变化 |
| 操作并发数 C | 同时尚未完成的操作数、限额及实际观测值 |
| 请求到达率 λ | 计划与实际发起速率、到达模式以及无法发起的请求 |
| 实例状态与负载 | 空闲、活跃或暂停，负载类型及活跃比例 |
| 沙箱规格 | 规格标识、请求的 vCPU／内存／磁盘及明确单位、实际生效资源配置；例如 2v2G、2v4G，具体档位与 G 的含义待确认 |
| 数据状态 | 镜像／快照大小、脏页量、工作集、快照链深度 |
| 缓存与预备状态 | 数据位置、各层冷热、预热／预取、预创建池 |
| 部署与时间条件 | 单机或集群、同节点或跨节点、观察时长及重复轮次 |

### Requirement: RT-07 跨方案外部语义对齐

系统 SHALL 先定义用户可观察的输入状态、操作、完成事件、正确性及输出，再结合对应版本源码与实际验证映射各方案的接口和内部阶段。内部阶段用于诊断，不要求所有产品有相同组件；不能仅按相同 API 名称认定操作等价。

#### Scenario: 同名恢复接口行为不同
- **WHEN** 一个方案恢复同一实例状态，另一个方案从磁盘重新启动新实例
- **THEN** 系统记录身份和状态语义差异，不能将两者作为未加说明的同一恢复能力排名

#### Scenario: 官方测量口径不一致
- **WHEN** 官方脚本分别测量 API 返回、业务就绪或整个用例耗时
- **THEN** 系统保留其原口径，按统一合同补充测量或标记不可直接比较，不仅重命名指标就声称已经对齐

### Requirement: RT-08 能力支持与测试覆盖分别记录

系统 SHALL 区分原生支持、组合操作实现、明确不支持和尚未验证，并另行记录测试是否执行及结果。官方脚本缺失不能直接认定能力不支持，尚未测量不能记为失败或零耗时。组合实现 SHALL 记录组成操作及完整成本。

#### Scenario: 功能存在但没有官方压测
- **WHEN** 源码及实际功能验证显示某能力存在而官方未提供性能脚本
- **THEN** 系统记录适配和补测需求，不将该能力列为不支持

#### Scenario: 候选明确缺少能力
- **WHEN** 某候选不具备本次所需能力
- **THEN** 报告记录能力缺口及选型影响，不把它混为性能脚本失败，也不静默删除该比较项

### Requirement: RT-09 功能验证先于性能结论

系统 SHALL 对适用场景验证真实状态变化、可执行性或结果正确性；性能采样中的每次操作仍需检查其完成结果。功能验证通过一次不能使后续全部请求自动计为成功，功能失败的计时必须保留但不得作为成功操作时延。

#### Scenario: API 返回成功但沙箱不能执行
- **WHEN** 创建接口返回成功而约定的 Guest 命令或业务就绪验证失败
- **THEN** 系统独立记录接口、状态及功能结果，不计入业务可执行成功吞吐；若所选创建终点为合同状态且已满足，保留对应状态创建计数和时延，不将其解释为命令功能已通过

#### Scenario: 克隆或快照功能验证
- **WHEN** 测试合同要求继承或恢复特定状态
- **THEN** 系统按声明检查状态及克隆独立性，性能结果绑定对应正确性证据

### Requirement: RT-10 计时事件与恢复后有效工作

系统 SHALL 区分接口返回、实际操作完成、可执行和首次有效工作完成等适用事件，分别定义起止位置、时钟和观测方式。创建及恢复不能只凭控制 socket 或进程存在宣称可用，删除不能只凭接口响应宣称资源已释放。

#### Scenario: 恢复完成后仍按需读取数据
- **WHEN** 恢复接口返回后首次任务仍需读取工作集
- **THEN** 系统分别记录恢复到可执行及首次任务完成时间，不将接口完成等同于工作集已全部就绪

#### Scenario: 删除异步回收
- **WHEN** 删除请求已响应而进程或资源尚未释放
- **THEN** 系统分别记录接口时延、终止及释放观测，并按合同判断完成状态

### Requirement: RT-11 逐请求时延与统计可靠性

系统 SHALL 保留逐请求时延、批次完成时间和摊销值的区别，分位数必须由对应口径的样本计算并标明样本数、重复轮次和波动信息。成功时延分布 SHALL 与失败、超时及其他结果共同报告，样本不足时不能把尾部分位数包装成稳定结论。

#### Scenario: 只有批次耗时
- **WHEN** 脚本只记录整批耗时和并发数
- **THEN** 系统可报告批次耗时及摊销值，但不能据此生成逐请求 P95 或宣称摊销值等于逐请求平均时延

#### Scenario: 成功样本有选择性
- **WHEN** 部分操作超时而成功请求较快
- **THEN** 系统同时展示超时数量及处理规则，不仅引用成功分位数宣称整体性能良好

### Requirement: RT-12 正确完成吞吐

系统 SHALL 分别记录计划发起、实际发起、接纳和正确完成的数量及速率，说明各自时间窗口；有完成期限时另报期限内正确完成量。业务提交或准入成功不能替代业务完成，重试和迟到完成应按合同单独归属。

#### Scenario: 请求大量被接纳但完成缓慢
- **WHEN** 控制面接受大量创建请求而只有部分实例就绪
- **THEN** 报告分别展示接纳和成功就绪吞吐，不用接纳速率代表创建完成能力

### Requirement: RT-13 资源分层与增量开销

系统 SHALL 区分宿主整体、平台常驻组件、单沙箱运行时与 Guest 内负载的资源观测，说明 CPU、内存、I/O 的口径和窗口，避免跨层重复相加。固定开销与实例增量开销分别报告；单位成功操作开销必须明确分子是否包含失败及共享服务成本。

#### Scenario: 多层内存观测重叠
- **WHEN** 同时采集宿主、进程或 cgroup 和 Guest 内存
- **THEN** 系统保留各层口径，不直接相加为总内存；共享页和不同内存指标不能混作同一计量

#### Scenario: 估计单实例底噪
- **WHEN** 比较不同实例数量下的资源开销
- **THEN** 系统保留基线与增量关系，不仅以全机资源除以实例数推导单实例固定成本

### Requirement: RT-14 密度并发与到达率独立

系统 SHALL 分别建模已有实例数 N、操作并发数 C 和请求到达率 λ。固定并发与固定到达率 SHALL 标明负载模型及实际实现值，不能因系统变慢使实际发起速率下降而仍声称维持目标速率，也不能把存量实例数当作请求并发。

#### Scenario: 存量密度下并发创建
- **WHEN** 已有 N 个沙箱时以 C 并发执行创建
- **THEN** 系统分别记录存量状态、实际操作并发及新增实例数，声明测量期间密度是否保持不变

#### Scenario: 负载发生器未达到目标速率
- **WHEN** 计划到达率高于实际发起速率
- **THEN** 系统报告差额及已知原因，不能将未实际施加的压力下结果作为目标速率测试通过

### Requirement: RT-15 单节点密度的条件化结论

系统 SHALL 同时支持将实例数作为测试条件，以及在明确时延、正确完成率、资源约束和观察窗口下求得可持续承载量。空闲实例容量与活跃工作容量 SHALL 分别报告；不能通过忽略拒绝、Guest 失败、OOM或工作丢失提高密度结论。

#### Scenario: 空闲实例多但活跃工作失败
- **WHEN** 节点能够创建大量空闲实例，而对应活跃负载出现失败
- **THEN** 报告区分空闲密度与活跃密度，不把前者当作后者的容量证明

### Requirement: RT-16 数据来源产物、启动路径与缓存准备成本

系统 SHALL 按来源产物 kind 与解析出的启动路径记录来源，而不只按接口名称记录“模板”或“快照”。来源产物 kind SHALL 至少区分镜像产物、可移植沙箱产物与快照清单；启动路径 SHALL 至少区分冷启动、内存恢复与磁盘恢复。当同一接口名称（例如“模板”）在不同候选或同一候选内可解析为多种产物 kind 或启动路径时，系统 SHALL 逐项记录实际 kind、launch path 及证据，不得合并为单一方法身份。系统 SHALL 记录其实际状态内容、数据位置及缓存／预备条件。从镜像创建 SHALL 区分完整准备路径与已准备路径，明确拉取、转换或模板构建成本是否计入，不能遗漏或重复计入一次性成本。

#### Scenario: 必须先把镜像转换为模板
- **WHEN** 某方案不能直接从镜像启动而需预先生成模板
- **THEN** 系统报告完整路径的转换及启动成本，并可另报模板已准备后的创建性能，不能将两种结果混用

#### Scenario: 缓存状态不一致
- **WHEN** 一个方案使用预热本地数据而另一个从远端首次读取
- **THEN** 系统记录差异并按合同分组或补测，不将两者直接标成同等冷启动条件

#### Scenario: 同一接口名称解析为不同启动路径
- **WHEN** 某候选的“模板”创建请求按其内部 kind 解析为镜像冷启动、沙箱冷启动或快照内存恢复
- **THEN** 系统分别记录该来源的产物 kind、启动路径与实际规格来源，不同路径结果不得合并为同一方法的时延或吞吐

#### Scenario: 名称与产物 kind 不一致
- **WHEN** 某候选的创建参数名为“模板”而实际解析为快照清单恢复
- **THEN** 系统按实际产物 kind 归入快照来源方法，并记录命名与语义差异，不因参数名称为“模板”就归入模板来源

### Requirement: RT-17 生命周期状态和产物语义

系统 SHALL 为暂停、恢复、克隆、快照及删除记录实例身份连续性、内存与磁盘状态、资源保留或释放行为。快照 SHALL 区分生成、发布、可恢复等适用完成点及逻辑大小、实际新增存储量，不能仅按接口名称或返回成功认定等价。

#### Scenario: 暂停仅停止执行但保留内存
- **WHEN** 某方案暂停后保留运行状态与内存资源
- **THEN** 系统报告停止执行时间和保留资源，不把该结果直接解释为资源回收完成

#### Scenario: 快照返回标识但尚不可恢复
- **WHEN** 快照接口返回标识而所需数据尚未完整可用
- **THEN** 系统分别记录返回和可恢复状态，按测试合同完成恢复验证后才给出对应成功结论

### Requirement: RT-18 测试设计与执行责任

系统 SHALL 将源码与接口语义分析、确定性测量和人工决策分工记录，模型分析必须关联对应候选版本的源码或文档证据并由实际验证补强。指标计算、条件展开和已明确断言由脚本执行，必要口径和选型取舍由人工明确。

#### Scenario: 生成候选方案测试适配
- **WHEN** 同一基础场景需要适配不同沙箱
- **THEN** 系统按下表形成证据及责任记录，未经验证的模型推断保持待验证，不进入已确认能力或性能结论

| 工作 | 脚本职责 | 模型职责 | 人工确认条件 |
|---|---|---|---|
| 场景和条件计划 | 校验结构、依赖、有限档位及覆盖情况 | 将需求拆成场景与条件草案 | 新增范围、档位、规模或优先级尚未明确 |
| 源码与语义分析 | 定位版本与入口，执行可验证检查 | 分析调用路径、状态语义、阶段和证据缺口 | 多种语义会改变比较目标且无法从既有要求决定 |
| 功能验证 | 执行断言、保留全部结果及状态证据 | 解释未覆盖异常 | 需要改变功能合同或授权范围 |
| 性能采集 | 按计划发压、记录逐请求及资源观测 | 诊断异常、提出补测建议 | 改变负载模型、资源档位或测试规模 |
| 分析与结论输入 | 统计、对齐检查、证据索引 | 解释差异、列明假设和适用边界 | 阈值、权重或业务取舍未确定 |

### Requirement: RT-19 沙箱规格作为独立实验条件

系统 SHALL 将沙箱规格作为独立条件轴，关联测试计划、请求、实例、结果和运行快照，记录规格标识、vCPU 数、内存及磁盘容量的明确单位、请求值与实际生效值。规格、资源预留或上限、实测占用 SHALL 分别表达；跨方案按规格及有效资源策略分组比较。平台最大／无约束配置不得静默解除测试指定的单沙箱规格约束；不支持、无法核实或生效不符须明确记录。

#### Scenario: 同一场景采用不同沙箱规格
- **WHEN** 用户选择 2v2G 与 2v4G 两个规格测试创建性能
- **THEN** 计划先明确 G 的单位并保留规范化容量，分别关联两个规格下的 N、C、负载及结果，不将不同规格样本混成一个未分组的时延或密度结论

#### Scenario: 请求规格与生效规格不同
- **WHEN** 请求的资源配置被平台默认值覆盖、候选不支持该规格或无法读取实际生效值
- **THEN** 系统保留请求和观测证据，分别标记不符、不支持或未验证，不静默替换规格后声称完成同规格比较

#### Scenario: 规格变化后重入测试
- **WHEN** 测试需求从一个规格改为另一个规格并恢复工作流
- **THEN** 系统创建新的条件版本并重新判定受影响结果的有效性，保留旧结果；模板或快照自带规格时核实其与目标规格是否兼容

### Requirement: RT-20 基础场景的稳态资源观测

系统 SHALL 在适用基础场景中同时支持峰值与稳态资源分析，区分生命周期过渡、空闲稳态和约定负载下的稳态。测试合同 SHALL 定义预热／排除区间、稳态判据、采样间隔、观察时长与等待上限，按实际时间窗口计算资源均值、分位数、波动或趋势等适用统计并保留原始序列。未达到判据或采集缺失不得宣称稳态已验证。基础稳态观测属于首阶段，不以低优先级长期运行场景为前提。

#### Scenario: 创建后进入空闲稳态
- **WHEN** 一批指定规格的沙箱创建完成并保留运行
- **THEN** 系统分别报告创建阶段峰值与满足判据后的空闲稳态资源，标明窗口、实例数和规格，不用启动峰值代替稳态占用

#### Scenario: 固定负载下观察稳态
- **WHEN** 测试合同要求在指定实例数与负载下持续观察资源
- **THEN** 系统记录实际负载和实例数，脚本按合同判断窗口并计算统计，注明 CPU 利用率分母、内存口径以及 I/O 与网络的速率或累计量，不将空闲结果当作负载稳态结果

#### Scenario: 未形成稳态或证据不足
- **WHEN** 等待达到上限仍不满足稳态判据，或样本缺口影响判断
- **THEN** 系统保留完整观测、判定原因与峰值结果，分别标记未达到稳态或无法验证；模型不得自行挑选平坦片段作为已通过证据

### Requirement: RT-21 按节点角色和组件归属分析资源

系统 SHALL 按环境、节点、节点角色、组件及实例建立资源观测归属，覆盖适用的管理节点管理进程、数据节点管理进程、数据节点沙箱运行时进程及其他必要组件。采集对象可为进程、容器或 cgroup，须记录身份、口径、时间与父子关系，保留节点整体、组件总量和适用单实例统计。共享服务、单节点角色共置及宿主／Guest 重叠统计 SHALL 明确边界，避免重复相加或无依据分摊。

#### Scenario: 多角色组件稳态资源报告
- **WHEN** 集群在某规格、实例数和负载条件下完成稳态观测
- **THEN** 报告逐节点区分管理节点管理组件、数据节点管理组件及沙箱进程的峰值与稳态资源，并关联同一实验窗口和原始证据；共享管理开销与单沙箱增量开销分别表达

#### Scenario: 单机共置角色或组件重启
- **WHEN** 同一主机同时承担管理和数据角色，或观测期间组件进程重启
- **THEN** 系统依据实际观测对象去重，并以进程启动身份或等价标识区分重启前后样本；无法归属的资源保留为未知，不从组件合计中静默丢弃

#### Scenario: 确定采集映射与计算职责
- **WHEN** 为候选沙箱建立角色、组件和采集对象映射
- **THEN** 模型依据版本化源码与部署证据提出映射，脚本验证对象并采集、判稳、聚合和检查完整性；口径或阈值无法从既有合同确定时由人工确认，模型解释不替代实测值

### Requirement: RT-22 可配置完成判据与事件时间域

系统 SHALL 分别定义 API 完整返回、合同状态就绪、服务端完成事件及首次命令完成，不强制把命令执行纳入创建时延。完成判据、观察方式及功能验证策略 SHALL 分别配置；状态及日志语义必须绑定源码和部署版本。客户端单调时钟耗时、轮询观察时间、服务端内部 duration 和日志采集到达时间不得混算。日志须关联具体操作及成功结果，缺失不能填零；跨候选只比较等价起止边界。

#### Scenario: 以状态判断创建完成
- **WHEN** 用例选择状态就绪作为创建终点
- **THEN** 系统核验该状态的承诺，逐实例记录观察到状态的耗时及轮询策略；命令可在停表后验证或单列，不把后验时间加回创建时延，状态成功与命令失败分别保留

#### Scenario: 使用 Kuasar 成功日志
- **WHEN** 日志包含本次创建的 sandbox launch terminal、成功结果及 starting_total_duration
- **THEN** 系统校验 sid、产品 run_id、kind 和起点证据，按服务端接纳后启动耗时报告；不把 startedAt 当 Running 时刻，不把内部耗时与客户端请求到状态耗时混成同一指标

#### Scenario: 日志延迟到达
- **WHEN** 服务端已完成但采集器稍后才观察到终态日志
- **THEN** 内部 duration 与观察时间独立保存，实际并发槽只能在获知完成后释放，不能用回溯时间虚构发压轨迹或客户端吞吐

### Requirement: RT-23 场景工作节点公共合同

每个用例 SHALL 具有稳定方法身份、有限条件集合、准备及测量边界、逐操作完成断言、资源采集、后验、清理、证据交付和重入规则。确定性请求循环及采样 SHALL 在脚本内执行，工作节点 agent 只加载必要合同及引用，组统筹二次复核。准备／功能预检不得隐式扩为其他性能矩阵；中断后先对账外部资源，不得用重试后的时间补造缺失的原始时延。

#### Scenario: 只选择恢复用例
- **WHEN** 对应环境缺少符合条件的已暂停实例
- **THEN** 节点准备并验证暂停 fixture，独立记录准备；只测计划内恢复方法，不附带创建、暂停的完整性能测试

### Requirement: RT-24 来源产物分层的创建用例

系统 SHALL 为每一来源产物 kind 与启动路径组合分别记录来源合同并给出稳定方法身份，而不是只按“模板与快照”两类划分。模板来源 SHALL 进一步记录其实际产物 kind（镜像产物／可移植沙箱产物／快照清单）；快照来源 SHALL 区分磁盘恢复与内存恢复。为镜像创建区分完整准备路径与已准备产物启动。完整路径包含候选必须的拉取、转换、构建、发布及启动，无法观测的阶段不得推测耗时，产物构建成本归属见 RT-41。共享一次构建再创建多个实例与独立完整创建 SHALL 分开标识，且每项成本只计一次；缓存和预检影响必须记录。

#### Scenario: 候选需要镜像构建或转换
- **WHEN** Cube 需要 build/job ready 或 Kuasar 需要合法 Image artifact 才能启动
- **THEN** 完整路径计入必要准备；若适配缺失则标待适配，不以预制模板或 artifact 的启动结果替代完整镜像创建

#### Scenario: 同一“模板”隐藏多条启动路径
- **WHEN** 某候选把镜像产物、沙箱产物与快照清单都命名为“模板”
- **THEN** 系统按实际 kind 与启动路径拆分方法身份，分别出具结果并标注跨候选可比条件

#### Scenario: 快照来源区分磁盘与内存
- **WHEN** 同一快照来源存在磁盘冷恢复与内存恢复两种启动路径
- **THEN** 系统分别记录两种方法的时延、吞吐与状态连续性证据，不合并为单一快照创建指标

### Requirement: RT-25 暂停恢复的状态合同

系统 SHALL 为暂停／恢复区分内存保留、磁盘冷恢复及适用的仅冻结语义，独立记录暂停、状态就绪、执行停止、资源释放和首次工作终点。恢复状态断言 SHALL 核验实例身份、适用的进程内存连续性及文件内容；不能仅凭 PID 或 API 成功判断。暂停观察不得触发自动唤醒，暂停后恢复验收不自动成为恢复性能样本。

#### Scenario: 内存与磁盘恢复不同
- **WHEN** 一种 profile 保持原进程内存而另一种仅从磁盘启动
- **THEN** 系统分别出具结果；内存恢复需验证进程内 token，磁盘恢复不得声称该连续性，状态恢复与首次工作耗时分别保存

### Requirement: RT-26 克隆的完整路径与逐子实例验收

系统 SHALL 区分从运行源完整克隆、预制快照 fan-out 和原生 fork 路径，记录捕获／发布、每 child 就绪、批次时间、源影响和部分失败。源最终状态及恢复源成本 SHALL 明确；要求源继续运行时完整路径包含必要恢复。内容继承和声明可写区域的隔离须验证，子实例数量、操作并发与存量实例数分别建模。

#### Scenario: fork 返回部分成功
- **WHEN** HTTP201 内包含成功 child 和错误，或 SDK 随后清理已成功 child
- **THEN** 系统逐项保留创建、后验及清理事实，不把父响应判为全成功；恢复先对账已有 child，不重放整个 fork 导致重复扩容

### Requirement: RT-27 删除的多终点与资源归属

系统 SHALL 按运行／暂停来源分别测删除，区分 API 返回、逻辑不可访问及资源释放，逐对象核验进程、挂载、网络和临时存储等适用资源。共享产物保留不得误判泄漏；无权限或网络故障不得当删除成功。删除结果不得覆盖创建事实，重复 DELETE 的耗时不得冒充首次删除时延。

#### Scenario: 逻辑删除后仍有资源
- **WHEN** 实例查询消失而本次拥有的运行时进程或网络对象仍在
- **THEN** 系统保留逻辑删除耗时，继续有界观察释放并报告残留或未知，不将 HTTP 成功等同于完整回收

### Requirement: RT-28 命令测试的协议与工作量

系统 SHALL 区分首命令、稳态、固定输出量及错误／超时功能用例，固定用户、命令、环境、连接、协议和输出条件。成功命令必须验证完整结束事件、退出状态和内容；start/PID 或 HTTP200 不代表完成。首次命令用例不得复用已执行过验证命令的实例并仍声称是实例首次执行。

#### Scenario: 命令超时但进程仍运行
- **WHEN** 客户端 deadline 到达或流中断
- **THEN** 系统记录超时及已知输出，按任务身份核验远端进程并清理；不默认成功，也不盲目重发造成重复副作用

### Requirement: RT-29 快照捕获发布与可恢复验证

系统 SHALL 分开定义本地捕获和约定范围发布，记录真实触页工作集、状态内容、存储后端、大小和源副作用，并用独立恢复核验可用性。捕获、发布完成及恢复验证耗时不得混为一个未注明边界的指标。组合快照须计入必要操作，无法取得独立阶段证据时只报告可观测总量。

#### Scenario: 快照返回但远端未就绪
- **WHEN** 本地快照存在而约定远端状态尚未完成
- **THEN** 系统可记录本地结果，但发布用例继续等待或失败；不以本地成功宣称跨节点可恢复，后验恢复时间另列

### Requirement: RT-30 密度双方法及协议保真

系统 SHALL 支持将 Cube 列表净增长方法和 Kuasar 固定 N 资源估算法迁移到所选候选，同时保留统一健康统计与修正估算。列表净增长与本批健康新增是不同停止方法；插入判稳、改变采样时刻、列表域或测试层次必须记录方法版本差异。实测规模、持续健康规模、预算下界及模型预测不得合并为同一种最大密度。

#### Scenario: 健康复验改变原方法节奏
- **WHEN** 移植 Cube 停止协议并增加逐实例验证或稳态等待
- **THEN** 系统保留原协议计数时刻，或明确采用修改后的方法版本；不得只保留公式就宣称完整复现原实验

#### Scenario: 固定 N 估算的数量和资源口径不符
- **WHEN** 请求实例数不等于实际健康数、资源域混用、成本非正或样本不足
- **THEN** 兼容值保留原分母及限制，统一预测标为无效或受限，不以请求数冒充真实实例分母，不把剩余预测容量称总实测容量

### Requirement: RT-31 密度联合资源采集与真实分母

密度用例 SHALL 在增长各批、固定 N 及最终窗口同步采集各角色节点／组件的 PSS、累计 CPU 时间和采样 CPU 峰值，保存实际实例身份及存活轨迹。单沙箱均值 SHALL 使用同一范围、同一窗口实际存活且满足声明状态的实例数，区分实例直接开销、共享平台摊销、相对基线增量及失败残留；不得以请求数作真实分母，或将增长全程 CPU 时间除以最终数量冒充稳态占用。

#### Scenario: 请求创建一批但只有部分拉起
- **WHEN** 仅部分实例实际存活且仍有失败资源
- **THEN** 系统报告 requested、实际存活和健康数；直接均值只用可归属存活实例资源及对应数量，失败残留单列，平台总成本摊销说明包含范围

#### Scenario: 聚合 CPU 峰值及稳态均值
- **WHEN** 不同组件在不同时间出现各自峰值
- **THEN** 各组件峰值分别报告，总峰值从对齐时间序列聚合后求最大，不相加各自峰值；稳态 CPU 时间、平均核占用及按实例摊销保留窗口和分母

#### Scenario: 部分实例资源采集缺失
- **WHEN** 部分存活实例的 PSS 或 CPU 未采集成功
- **THEN** 系统不把部分资源和除以全体实例数作为总体平均；可报告同一可观测子集的均值与覆盖率，总体结果标不足。暂停后正常卸载须有对账证据才记该项为零，不能将未知当零

### Requirement: RT-32 基于 PSS 的底噪与 Guest OS 扣除

底噪用例 SHALL 以进程 PSS 为主要内存依据，保留零实例平台基线及指定运行／暂停实例窗口，并保存原始 PSS、拟扣除 Guest OS 项、扣除方法和有效性。Guest OS 的边界及与宿主 PSS 同域归属必须明确后才可输出净底噪；不得减去配置内存、Guest 内任意 used 值或未验证常数。无法分离时保留原始测量并标净值待验证，不静默改用 RSS。

#### Scenario: 无法可靠分离 Guest OS
- **WHEN** 已取得 runtime PSS 但无法证明其中 Guest OS 部分的归属
- **THEN** 系统保留原始 PSS、映射与缺口，不输出虚假的净底噪；只使净值指标受阻，不丢弃已有效采集的数据

### Requirement: RT-33 扩展场景节点保留

系统 SHALL 为 E01–E06 保留工作负载、回滚／重置、混合长稳、压力、共置干扰及故障恢复的可选节点合同，复用公共采集和交付步骤。扩展的具体适配未审计时须标待验证，未纳入计划时不得执行或阻塞基础场景。故障和压力动作必须绑定明确对象、预算及恢复合同。

#### Scenario: 基础测试出现异常
- **WHEN** B 场景失败且模型建议故障或压力专项
- **THEN** 系统记录建议及证据，不自行扩大到 E04/E06；已有范围内的重试、对账和清理仍继续完成

### Requirement: RT-34 固定请求预算下的并发与节奏对比

密度场景 SHALL 支持固定创建请求总数 Q_total、改变并发 C 的滑窗及分批两种方法，同步采集性能和各角色／组件资源，并保留成功实例至最终观测。滑窗在任一请求达到所选完成点、失败或截止后补槽；分批在本批全部终结后等待指定间隔再发下一批。失败消耗请求预算，不自动补齐成功数；两种模式使用同一规格、初始存量、来源、完成合同及明确缓存条件。

#### Scenario: 滑窗维持在途上限
- **WHEN** 计划 C=20 且仍有未提交预算
- **THEN** 系统最多保持20个未完成创建，一个终结便补下一个，不等待整批；异步接口返回接纳时不提前释放以状态完成为终点的槽位，记录实际在途及补槽间隙

#### Scenario: 分批创建和最后不足一批
- **WHEN** 计划每批 B 个、并发上限 C、批间等待已明确
- **THEN** 系统等待本批所有请求终结后才开始间隔；剩余请求不足 B 时只发剩余数量，最后一批后不附加批间等待；B不等于C时标明批内限流语义

#### Scenario: 比较吞吐、资源和实际密度
- **WHEN** 相同 Q_total 在不同 C 和模式下运行结束
- **THEN** 系统分别报告包含批间等待的整轮吞吐、活动吞吐、失败、实际发起和最终存活数量；按同窗口真实 cohort 计算 PSS／CPU 开销，不把固定预算结果称为最大容量

#### Scenario: 中断或提前停止固定预算实验
- **WHEN** 运行因预算限制或中断未完成所有计划请求
- **THEN** 系统保留已消耗预算、在途操作及实际压力轨迹；先对账再处置剩余，不重置总数，也不把断续或未完成实验无条件用于完整连续实验排名

### Requirement: RT-35 测试工作节点的脚本化边界

系统 SHALL 按 N00–N10 及 B01–B10、E01–E06 的具体方法声明脚本／模型／人工职责，并提供内部 Mermaid。确定性前置、发压、观察、采样、计数、断言、统计、清理及交付由脚本执行；模型负责新源码语义、未知适配及异常解释，人工只明确未定义条件和范围。每方法须标实际实现和验证状态，不能因存在原脚本或流程图即称已脚本化完成。

#### Scenario: 按工作节点检查测试自动化范围
- **WHEN** 为选定场景生成工作实例
- **THEN** 按下表和 [完整逐方法职责表](../../node-automation.md) 绑定执行合同，并使用 [节点内部图](../../node-workflows.md)

| 节点 | 脚本化职责 | 非脚本化部分 |
|---|---|---|
| N00/N01 | 合同校验、外部操作及资源对账、复用判定 | 模型解释冲突；必要意图由人工决定 |
| N02/N03 | 前置准备、真实功能预检、复位及条件证明 | 缺适配的语义分析；条件缺失不可猜 |
| N04 | 角色／组件映射刷新、PSS/CPU、资源／日志／事件基线与采集 | 新 runtime 归属审计、Guest OS 减项边界 |
| N05、B/E 方法 | 全部有限发压、状态／事件观察、协议处理、断言、停止与预算 | 模型不参与逐请求循环；未知异常走公共协议 |
| N06 | 后验、最终 cohort、资源完整覆盖、稳态／回收窗口 | 无规则可解释的语义矛盾 |
| N07/N08 | 封存、质量检查、公式、吞吐及局部摘要 | 解释不替代数值；未定公式需明确 |
| N09/N10 | 本次资源清理、残留核验、分离状态及交付 | 未知清理诊断或超范围处置取舍 |

### Requirement: RT-36 密度过程同步创建吞吐

所有密度方法的实际创建过程 SHALL 同步记录唯一操作的发起、接纳、所选成功终点、失败及迟到事件，脚本生成固定一秒窗口的创建成功速率曲线及明确窗口的整轮吞吐。统计 SHALL 保留完成判据、时钟域、桶时长、去重及缺测状态，不能把异步接纳或最终存活数替代成功创建数量。分批等待计入整轮节奏，活动吞吐另列。

#### Scenario: 密度增长期间实例陆续创建成功
- **WHEN** 多个创建操作在不同秒达到所选状态或命令终点
- **THEN** 脚本按观察事件及操作身份去重，在各一秒桶计数；最后不足一秒的桶保留实际时长，资源时间序列与吞吐曲线可关联

#### Scenario: 批间等待与事件丢失
- **WHEN** 某一秒没有完成事件
- **THEN** 仅在采集完整时记真实零创建；采集缺失标未知，迟到完成单列，日志内部时间与客户端观察曲线不得混算

#### Scenario: 创建后退出或复用已有实例
- **WHEN** 已创建实例随后退出，或外推／SLO 方法复用已有实例没有新建
- **THEN** 退出不抹掉历史创建事件，最终密度独立统计；本轮无创建则吞吐不适用，前置创建吞吐标准备阶段，不冒充受控压力能力

### Requirement: RT-37 测量节点前置顺序与有效分支

需要零实例或明确初始存量基线的用例 SHALL 先准备来源和探测复位，再取得基线，最后创建待测 cohort。节点缺合同、缺适配或存在阻塞性未知副作用时不得进入测量。选择 EXEC_COMPLETE 时 SHALL 先执行并验证命令再关闭对应计时，选择状态／内部终点时先记录该完成事件，再按策略执行独立后验，不形成先等待命令完成再执行命令的依赖环。

#### Scenario: 底噪或外推准备了目标实例
- **WHEN** N02 发现本轮待测 cohort 已被提前创建而当前合同要求空实例基线
- **THEN** 系统按所有权和合同复位或声明基线无效，不将此时资源作为零实例基线，也不直接进入有效增量计算

### Requirement: RT-38 测试执行代码与独立契约验证

每种测试方法 SHALL 具有可追溯的执行代码设计、实现模块、输入输出合同、失败恢复、原始证据与对应代码契约测试。契约测试 SHALL 用独立已知值或参考协议验证完成判据、发压节奏、资源归属和公式，区分算法、协议、恢复和真实环境验收；不得用被测计算函数生成其自身预期值。

#### Scenario: 验收滑窗或资源测算实现
- **WHEN** 测试器实现了滑窗、分批、吞吐、PSS摊销或CPU峰值
- **THEN** 用固定事件轨迹和独立预期数值验证，包含异步接纳、部分失败、缺测、错时钟和错分母反例；不能只检查返回字段存在

#### Scenario: 受控服务测试通过
- **WHEN** 产品适配通过受控HTTP或合成fixture验证
- **THEN** 只提升相应代码契约验证状态，真实候选的功能和性能仍需版本限定的实际证据；未提供环境保持未验证

### Requirement: RT-39 执行器请求预算与副作用恢复

测试执行器 SHALL 持久记录请求槽、子操作、提交许可与资源身份，预算消耗及已知副作用不得因重入重置。客户端超时与服务端真实在途 SHALL 分别追踪，未知副作用达到约定上限时停止新增并对账；命令、构建、克隆和清理同样遵守该协议。

#### Scenario: 响应丢失后重入
- **WHEN** 远端可能已执行创建或构建而本地没有结果
- **THEN** 使用原操作关联进行查询，只有已验证幂等协议才同键重放；无法确认则保留unknown，不能新建操作冒充首次提交或补造原始时延

### Requirement: RT-40 来源产物身份与解析证据

系统 SHALL 为每个创建或恢复实验记录来源产物的身份、解析出的启动路径及其证据来源，不把接口参数名称当作能力或语义。来源产物身份 SHALL 至少包含产物 kind、产物标识与版本／digest、生产者步骤（现有产物／构建作业／捕获发布）以及数据位置与缓存状态。启动路径 SHALL 由源码与实测共同确认，至少区分冷启动、内存恢复与磁盘恢复，并记录该路径决定的规格来源（请求显式声明或从产物继承）。无法从源码或实测确认解析结果时 SHALL 标为未验证，不得按名称推断。跨候选比较 SHALL 先对齐产物 kind、启动路径与规格来源，仅名称相同不得视为等价。

#### Scenario: 参数名称相同而产物 kind 不同
- **WHEN** 两个候选都把创建参数命名为“模板”，但一个解析为镜像产物冷启动、另一个解析为快照清单内存恢复
- **THEN** 系统分别记录产物 kind 与启动路径，标记二者不构成同一方法的等价比较

#### Scenario: 规格来源不一致
- **WHEN** 一个候选从请求显式取规格，另一个从来源产物继承规格
- **THEN** 系统分别记录规格来源并保留实际生效规格证据，跨候选按规格与来源分组，不静默替换

#### Scenario: 无法解析来源产物
- **WHEN** 缺少源码版本或无法获取产物身份证据
- **THEN** 系统保留已有观测并标记来源产物身份未验证，不据命名推断 kind 与启动路径

### Requirement: RT-41 来源产物构建场景目录

系统 SHALL 为来源产物的生产提供独立可测场景，与 B01–B10 的实例操作场景分开，至少包括从镜像／基础产物构建模板产物，以及从已有模板／镜像产物构建快照产物两类。构建场景 SHALL 记录构建作业／捕获发布的完成判据、构建时延分位数、构建吞吐、构建期 CPU／内存峰值、产物大小与新增存储、冷热缓存分列，以及失败与重入语义。构建产物的一次性成本 SHALL 只在其归属场景或显式计入的用例中计一次，不得在创建场景（B01／B02）中重复计入，也不得默认隐藏。构建场景 SHALL 明确其与 B02.FULL 的镜像准备阶段及 B08 快照捕获的边界，避免同一动作在两个场景下重复报告。

#### Scenario: 从镜像构建模板产物
- **WHEN** 候选需要异步构建或转换作业才能得到可创建模板产物
- **THEN** 系统记录构建提交、作业状态与就绪／错误终点的时延与吞吐、构建期资源峰值、产物大小及缓存状态，并标明该成本不计入后续创建时延

#### Scenario: 从模板构建快照产物
- **WHEN** 候选需要从已有模板或镜像产物构建可再创建的快照产物
- **THEN** 系统独立记录该构建路径的完成判据与成本，不把它与从运行实例捕获的 B08 或从快照恢复的 B01.SNAPSHOT 混为同一方法

#### Scenario: 构建产物被后续创建复用
- **WHEN** 同一构建产物被多个创建用例复用
- **THEN** 系统按产物身份记录共享关系与复用次数，构建成本只计一次，独立完整创建与共享构建后创建分别标识

#### Scenario: 背景沙箱密度下的构建
- **WHEN** 构建用例声明背景沙箱密度（先创建 N 个背景沙箱）
- **THEN** 系统在背景存在下测量构建时延与**增量**资源（total − 背景基线），并记录背景实际值；不得把背景沙箱计入构建产物分母；构建本身不要求并发构建请求密度

#### Scenario: 构建期资源与产物大小
- **WHEN** 构建到达 ready
- **THEN** 系统记录构建期 CPU／内存峰值、产物大小与新增存储、冷／热缓存状态；缺证据标 unavailable 不补零

### Requirement: RT-42 创建端点的拓扑可及性与同步/异步语义

系统 SHALL 把创建端点的实际拓扑与完成语义作为显式实验条件记录，至少区分经管理面/ingress（router）入口、经数据面节点 API 入口、以及同机 CLI 注入就绪信号三类。系统 SHALL 记录每个候选创建调用返回时实例所处的真实状态（进行中或已就绪），并据此确定所选完成判据是否需要额外的状态观察。当同一候选存在多个可及入口时，系统 SHALL 分别记录各自入口与端点，不得合并为同一方法结论。请求管理面入口前，系统 SHALL 先核验该部署确实包含管理面/ingress 角色与组件；仅有数据面时不得假定管理面入口可用。涉及进程内就绪信号注入时，系统 SHALL 将其记录为独立的白盒端点并声明其内部里程碑。无法从源码或实测确认入口的同步/异步语义时，系统 SHALL 标为未验证，不得按接口名称推断。

#### Scenario: 管理面入口同步到就绪
- **WHEN** 部署包含管理面/ingress 角色，且创建请求经该入口返回时实例已经就绪
- **THEN** 系统将该次调用记为同步完成，`API_COMPLETE` 与 `STATE_READY` 为同一时刻，不得再额外报告一次就绪等待延迟

#### Scenario: 仅有数据面入口的异步创建
- **WHEN** 部署只有数据面节点，且创建请求返回时实例仍处于进行中状态
- **THEN** 系统分别记录受理时刻与状态就绪时刻，按合同轮询至目标状态，且不得把受理成功当作创建完成

#### Scenario: 同机注入就绪信号
- **WHEN** 测试器与节点同机并注入进程内就绪信号
- **THEN** 系统将其记录为独立白盒端点，声明其所处的内部里程碑，并禁止与黑盒状态就绪端点的样本并入同一列比较

#### Scenario: 无法核验管理面角色
- **WHEN** 用例声明管理面入口，但环境核验未发现管理面/ingress 角色或组件
- **THEN** 系统将该用例标为阻塞并建议改用数据面入口，不得静默回退或据接口名称假定其可用

### Requirement: RT-43 测试间环境还原与残留核验

系统 SHALL 在测试与测试之间还原环境，删除本轮用例创建的沙箱，并 SHALL 区分本轮归属的实例与预热池、空闲池及预先存在的实例。删除 SHALL 采用小批量、多轮次与轮间间隔，不得一次性全量删除。系统 SHALL 只删除归属于本轮运行标记（例如创建时写入的运行标识）的实例，并 SHALL 显式排除预先存在的基线实例。删除完成后，系统 SHALL 重新枚举并核验是否仍有本轮归属实例残留；存在残留或删除失败时 SHALL 报告为不完整而非成功。对删除为异步的产品，系统 SHALL 在核验前等待稳定，不得把“已接受删除”当作“已删除”。系统 SHALL 记录每轮删除数量、失败及残留身份，并区分实验资源清理与证据清理。

#### Scenario: 小批量多轮删除
- **WHEN** 本轮创建的沙箱数超过单批上限
- **THEN** 系统按批大小分多轮删除、轮间保持间隔并记录每轮删除数量，不得一次性全量删除

#### Scenario: 预热池与基线实例
- **WHEN** 节点上存在预热池、空闲或预先存在的实例
- **THEN** 系统只删除本轮运行标记归属的实例，预热／空闲／基线实例不被删除，也不因其存在而判定还原失败

#### Scenario: 异步删除后的残留核验
- **WHEN** 产品的删除为异步，删除刚返回但实例仍处于删除中
- **THEN** 系统在核验前等待稳定；仍未消失的本轮实例记为残留，整体状态为不完整

#### Scenario: 删除失败
- **WHEN** 某个实例的删除请求失败
- **THEN** 系统记录失败身份并计入残留，不把该实例当作已删除

### Requirement: RT-46 操作的同步/异步终点与同步时延口径

系统 SHALL 为每个生命周期操作（创建、暂停、恢复、克隆、删除、快照）记录其**同步/异步终点**：同步终点表示调用返回时已达目标状态（`API_COMPLETE` 即 `STATE_READY`）；异步终点表示返回仅为**受理**，须轮询到目标状态。系统 SHALL 只把**同步完成**记为对应操作的时延；异步入口 SHALL 在目标状态（如 `running`／`paused`／逻辑不存在）下停表，不得把受理时延冒充完成时延。当同一操作在管理面/ingress 与数据面入口的同步性不同时（例如创建），系统 SHALL 分别记录入口与终点。无法从源码或实测确认同步性时 SHALL 标为未验证，不得按接口名称推断。

#### Scenario: 同步操作直接停表
- **WHEN** 暂停、删除等操作在所选产品为同步
- **THEN** `API_COMPLETE` 即 `STATE_READY`，以调用返回停表，不再轮询

#### Scenario: 异步受理须轮询到终点
- **WHEN** 创建（Kuasar 数据面）或恢复（Kuasar）返回仅受理
- **THEN** `api_complete_s`（受理）与 `state_ready_s`（到 ready）**分列**，以到达目标状态停表

#### Scenario: 同一操作入口同步性不同
- **WHEN** 创建的 router 入口同步而 node 入口异步
- **THEN** 分别记录入口与同步性，不合并为同一方法或同一时延列

#### Scenario: 无法确认同步性
- **WHEN** 缺源码或实测证据
- **THEN** 该操作端点标为未验证，不默认同步或异步

### Requirement: RT-47 创建时延的客户端口径（对齐官方基准）

系统 SHALL 以可与产品官方基准基准可比的口径测量**同步创建**的时延：

- SHALL 在**复用且预热过的连接**（keep-alive／连接池）上发压；每请求新建连接的 TCP／TLS 握手**不得**计入创建时延；
- 对同步入口 SHALL 以**响应头到达时刻**（`api_headers_s`）停表；把“读完响应体”（`api_complete_s`）与“JSON 解码”的时刻**分列**记录，不得把整包读取计入对标官方口径的创建时延；
- SHALL 记录并公开**口径版本**、连接池配置（每主机复用数、idle 超时）、**预热轮次与是否排除在统计外**；口径版本 SHALL 进入可比性键；
- 异步入口（如 Kuasar 数据面）SHALL 轮询到目标状态再停表，且轮询间隔 SHALL 足够密（相对 ms 级创建），否则标为未验证；
- 找不到口径/同步性证据时 SHALL 标为未验证，不得默认复用官方口径。

#### Scenario: 与官方同口径的同步创建
- **WHEN** 在复用并预热的连接上、对同步入口以响应头停表测创建
- **THEN** 得到可与官方基准直接对比的 `create_latency`，并记录口径版本与预热排除

#### Scenario: 未复用连接或计入握手的测量
- **WHEN** 每请求新建连接或把整包读取计入时延
- **THEN** 该样本不归入官方同口径列；按口径版本分组或标为不可比，不得混成一个创建时延结论

#### Scenario: 整包读取耗时分列
- **WHEN** 响应体较大或分批到达
- **THEN** 响应头→完成的时间单独记录，不并入创建时延，也不被当作创建完成

#### Scenario: 缺口径证据
- **WHEN** 未提供连接复用/预热/停表点证据
- **THEN** 该测量标为未验证，不声称与官方可比

### Requirement: RT-48 资源观测合同的强制声明与缺失显式化

系统 SHALL 使批量窗口的资源采集（PSS/CPU）呈现为“已声明并采集”或“显式失败/缺口”，**不得静默跳过**：

- 未声明 `CaseContract.resources` 的需测方法 SHALL 记入 `evidence_gaps`（如 `resource_observation_not_requested`），不得只给无来源的 `missing_resource_evidence`；
- 声明后缺采样器或装配输入（进程 inventory、collector 绑定、guest 扣减）SHALL `blocked` 并报具体缺失原因；
- 样本不足 SHALL 记 `unavailable/insufficient_samples`，数值保持缺失，不得补零或由夹具推默认。

#### Scenario: 未声明资源合同的真实运行
- **WHEN** 真实 runner 用例未声明 `resources` 却运行
- **THEN** 结果含显式证据缺口（`resource_observation_not_requested`），且不声称已测得 PSS/CPU，而非只给无来源的 `missing_resource_evidence`

#### Scenario: 声明资源合同但缺采样器或清单
- **WHEN** 用例声明 `resources` 但未提供采样器、真实 inventory 或 collector 绑定
- **THEN** 运行 `blocked` 并给出具体缺失原因（如 `resource_sampler_required`、inventory 不一致），不静默跳过

#### Scenario: 清单身份或域不匹配
- **WHEN** inventory 缺 `node/boot_id/processes/evidence_ref` 或与读数域（procfs boot/scope）不一致
- **THEN** 拒绝装配/运行，不构造采样器

#### Scenario: 短寿命场景窗口覆盖不足
- **WHEN** 创建型沙箱存活期短于测量窗口所需（基线→稳态→关闭），或采样窗口参数/覆盖率不足（`interval_s/window_s/max_wait_s/max_gap_s/min_samples`）
- **THEN** 标 `insufficient_samples`/未验证，或改用长寿命场景；不补样、不补零

#### Scenario: 样本不足或缺失
- **WHEN** 采样序列为空或低于 `min_samples`
- **THEN** 资源结果记 `unavailable` 并附覆盖率与缺口引用，数值保持缺失，不从夹具推默认
