# Proposal

## 当前工作区

2026-10-24：生命周期代码、规格、设计、任务和验证资产已合入本项目根目录。以根目录工作区为审阅对象；原工作树仅保留历史资产，不能再以“主目录未合入”解释当前状态。未自动提交或推送。当前边界见 [能力账本](../../../docs/orchestration/lifecycle-status.md) 与 [继续实施记录](../../../docs/verification/agent-lifecycle-runtime/continuation-20261024.md)。

## Why

沙箱选型需要一套端到端、可重入、可按需求增量修改的测试工作流，使性能结论能够追溯到环境、测量口径和原始证据。将确定性操作脚本化，并隔离各节点 agent 的上下文，可以减少重复执行、token 浪费、无证据判断及上下文压缩后的信息丢失。

## 当前实施范围（2026-10-23）

当前已在根目录实现：节点生命周期/双层预算/原操作对账、已登记动作与恢复计划、应用内 provider 和持久角色任务、实际候选 CAS 编辑与冻结、独立 reviewer、候选外可信观察器、bundle/worker 版本绑定、晋级事务、发布后观察、回退和 rollout。普通 env/eval worker 按显式配置装配这些服务；没有配置或能力时保留具体 blocked 原因。

本地测试不替代专用 PostgreSQL、真实 Bubblewrap、外部 provider 或三产品部署验收。完整数据库硬杀矩阵、远端 bootstrap/制品投递、部分运行时参数和动态产品归属发现仍有代码工作。task checkbox 仅表示该行完整验收完成；已实现但包含未执行 live 验收的行仍不勾选。详情与实际日志见 [继续实施记录](../../../docs/verification/agent-lifecycle-runtime/continuation-20261024.md)。

目标合同由下文及 specs/design 定义；当前差额不降低目标要求，OpenSpec planning complete 只表示规划产物齐备。

## What Changes

2026-10-24 后续修复：端到端检查发现的 R1（drain 被取消）、R2（停止后角色入队）、R3（父级漏计子 provider）已按 TDD 修正，25项专项通过；规格、ALD-11、ATG-08 和45.4-B/C同步。完整45.4仍未勾选，任务总数160/209不变。详细行为及回归范围见 [修复证据](../../../docs/verification/agent-lifecycle-runtime/stop-fixes-20261024.md)。

- 2026-10-22 补全 WF-39：工作节点有界自修复、受限 agent team、隔离候选代码/图迭代、可信测试门禁与新版本运行。详见 [生命周期详细设计](agent-lifecycle-design.md)、[测试门禁设计](agent-lifecycle-test-gates.md)、[tasks 42–49](tasks.md)；交接审阅缺口与真实租约门禁已纳入 ALD-10/ATG-07；用户已授权进入 apply，逐项实现状态以 tasks 与实施记录为准。

- 定义五个大颗粒阶段：环境检查、环境配置、指标测试、数据分析、生成结论归档；阶段内部允许继续细化节点。
- 定义主 agent、环境组统筹 sub-agent、组内工作节点 sub-agent 的三层看护、上下文边界与分层状态；确定性操作由脚本执行，明确模型判断和人工确认的适用条件。
- 定义持久状态、断点恢复、失败重试、局部重跑、需求变更后的增量执行，以及图节点和依赖的增删改查。
- 支持按优先级、环境组、沙箱类型及具体用例组合选择执行范围；通过依赖检查形成有限执行计划，保留选择、复用和覆盖记录。
- 定义环境声明、当前观测、运行快照与原始证据之间的关系，确保复用可验证、失败不丢失、结论可追溯。
- 细化单节点和多节点环境的连接、密钥、角色、安装、配置、复检及报告要求。
- 定义已安装环境与新安装环境的统一报告合同，并区分在位证据和实际安装历史。
- 固化运行时测试的场景、条件参数及指标三层合同；首阶段覆盖十类基础场景，先验证功能，再评价基础功能性能。
- 保留六类补充场景作为低优先级需求，不将其纳入首阶段默认完成门槛；明确跨方案语义对齐、能力覆盖和性能证据口径。
- 将沙箱规格纳入实验条件及有效配置核验；基础阶段按节点角色与组件分析峰值和稳态资源，并在环境报告中提供观测对象映射。
- 定义测试节点自检、环境组二次复核及组内分析、主 agent 侧统一分析的分工；脚本测算指标并生成可追溯 Excel，结论阶段结合脚本化事实交付与模型解释。
- 支持已验收组结果的增量分析与阶段交付；最终统一分析必须包含横向对比，报告基于对比给出选型结论及限制，不能只拼接各组交付件。
- 基于三套源码审计展开全部基础场景及低优先级扩展的用例节点，区分创建状态完成、服务端日志耗时及命令验证，明确各场景计时、断言、证据与重入合同。
- 逐工作节点明确确定性脚本、模型判断、必要人工及实现状态，绘制节点内部 Mermaid；密度过程同步输出每秒成功创建数与整轮创建吞吐。
- 细化来源产物语义与构建场景：创建方法身份由来源产物 kind 与解析出的启动路径决定，不按接口参数名称；模板来源钉死产物 kind，快照来源区分磁盘／内存；新增 B00 来源产物构建场景目录（构建模板产物／构建快照产物），构建成本只计一次且不与 B02.FULL、B08 重复。
- 本 change 包含需求、设计、测试门禁、实施 tasks 与逐项实现；用户已授权进入 apply。真实部署与性能实验依据具体环境合同执行，当前生命周期增量的实现/验收边界见上表。

## Capabilities

### New Capabilities

- `evaluation-workflow`：五阶段选型工作流的编排行为、执行责任、状态恢复、变更管理、证据流转与结果交付。
- `environment-readiness`：按环境及节点角色检查、配置并验证测试准备状态，交付可追溯的环境报告。
- `runtime-evaluation`：运行时基础场景、功能验证、性能指标与条件矩阵、跨方案测试语义及低优先级扩展目录。

### Modified Capabilities

无。当前项目没有已有的正式 OpenSpec capability。

## Impact

- 规划归属为 `sandbox_graph` 根目录，覆盖跨候选沙箱的选型工作流；本次不修改 `AgentENV`、`CubeSandbox`、`kuasar-components` 或 `kuasar-sandbox` 的产品代码。
- 后续可评估复用各项目的部署、环境检查、性能 harness、结果校验和报告能力，不默认已有工具已经满足统一合同。
- 框架、持久化后端、执行器和产物存储的工程基线见 orchestration-design D01；产品适配及真实测试参数仍需按合同逐项确认。
- 当前交付为本 proposal、三份 delta spec、`design.md` 主图、`test-nodes.md` 场景节点、`node-automation.md` 职责和状态表、`node-workflows.md` 节点内部 Mermaid；另含 `orchestration-design.md` 代码设计、`orchestration-test-design.md` 工程测试设计与 `tasks.md` 实施清单；这些文件承载目标合同；已有代码和已验证范围另由 tasks、实施记录及原始证据列明。

## Clarification Record

### 已确认的需求

下列为按讨论顺序保存的确认记录；早期“先设计/暂停”描述对应当时阶段，后续第37项及生命周期 apply 授权已进入实施。当前进度以上方实施范围和 tasks 为准。

1. 五个大颗粒阶段如上，支持单节点及多节点、不同节点角色和不同沙箱类型。
2. 确定性操作脚本化；主 agent 看护全流程；节点 sub-agent 仅掌握自身所需上下文。
3. 工作流可重入，且可随测试需求变更或补充，对图节点和依赖进行增删改查。
4. 环境信息有固定格式；优先取用已有信息并验证，缺失信息由探测或用户补充。
5. 连通性检查、密钥配置、安装检查、按需安装配置及安装后复检均需自动化。
6. 新安装与已安装环境均输出节点属性和证据；新安装还保留实际步骤及结果日志。
7. 选型测试需避免不必要的默认配置约束；“最大／无约束”的具体范围尚待确认。
8. Spec 必须明确脚本、模型、人工的职责及确认条件，避免每一步都询问用户。
9. 当前选型重点是基础功能及基础功能性能；每个适用场景先验证真实功能和结果正确性，再评价其性能。
10. 首阶段场景为：从模板／快照创建、从镜像创建、暂停、恢复、克隆、删除、命令执行、快照、底噪、单节点部署密度。
11. 补充场景全部降低优先级：沙箱内负载执行性能、快照回滚／状态重置、混合生命周期与长期运行、资源弹性与压力下运行、共置负载干扰、故障后恢复性能。它们保留在需求目录，但不阻塞首阶段交付。
12. 区分场景、条件参数、指标；已有实例数 N、操作并发数 C、请求到达率 λ 分别描述。按确认的条件矩阵执行，不默认全量笛卡尔积压测。
13. 固化时间、吞吐、可靠性与正确性、资源与效率、容量与稳定性、状态与产物六类指标；按场景适用性分配，不要求每场景采集所有扩展指标。
14. 统一外部可观察的输入状态、操作、完成事件和正确性，再深入源码映射各候选的接口和内部阶段；官方测试缺失不等于能力缺失。
15. 逐请求时延、批次完成时间与摊销值分别报告；正确完成吞吐与请求接纳量分开；资源分层计量，样本数、失败及波动信息完整保留。
16. 沙箱规格是独立实验条件，例如 2v2G、2v4G；需区分请求规格、实际生效配置和实际占用。示例不是完整或强制档位，具体单位及档位留待确认；平台放宽限制不覆盖单沙箱测试规格。
17. 基础评估除峰值外还需稳态资源分析，区分空闲和约定负载，按节点角色和组件归属报告管理节点管理进程、数据节点管理进程、数据节点沙箱进程等。基础稳态不因长期运行场景优先级较低而延期。
18. 环境报告提供观测映射与发现规则，运行时补齐动态对象；判稳、采集与统计脚本化，模型解释证据，未明确的口径和阈值由人工确认。具体稳态判据与采样参数尚未冻结。
19. 指标测试支持选择多个环境组，采用主 agent → 环境组统筹 agent → 组内工作节点 agent 的层级；各组和节点具有独立的必要上下文，由主 agent 统一调度。
20. 节点负责测试、自检、局部分析及节点状态；组统筹对测试数据、日志、报告等交付件二次看护，负责组内分析与组级状态；主 agent 维护全局调度及汇总状态。状态持久保存，复核记录不能覆盖原始事实。
21. 数据分析是主 agent 侧的统一阶段，但不取代节点自检及组级分析校验；具体指标由脚本统一测算，规范化结果汇总到 Excel，原始证据仍独立保留。
22. 环境组按每一套具体环境划分，可为单节点或多节点集群，一组由一名当前负责的统筹 agent 统一管理。单节点也须区分是否承担管理角色；组内管理、数据等角色均归属同一组统筹。相同候选部署于不同环境时仍是不同组，图工作节点与物理节点分别标识。此项解决 Q9。
23. 各组验收后允许增量分析和输出明确标注范围的阶段 Excel；本轮所有计划组具有明确的成功、失败、跳过或阻塞结论及处理记录后统一收口，缺失与失败保留，不要求所有候选测试通过。Q10 的汇聚方式已解决，并行与资源隔离细则仍待明确。
24. 选型评估必须完成跨候选横向对比。定量比较、可比性检查和对比表归属数据分析阶段；报告阶段消费这些产物，综合说明优势、限制和选型建议。最终收口不能仅拼接组报告；具体比较基线、偏好和评分权重仍未冻结。
25. 默认报告形式确定为“分场景横向对比＋适用场景推荐”。综合评分和总排名保留为可选项，明确启用并确认指标、权重及评分规则后再计算；未启用时不因缺少权重阻塞交付。Q11 的默认结论形式已解决，模板及归档要求仍待细化。
26. 工作顺序明确为源码审计、测试方法与节点细化、Mermaid 工作流设计、确认后实现 LangGraph 调度、再接入具体测试脚本。不用 Archify 演示图代替图工程工作流；此前提前产生的脚本草稿停止实现，等待图设计复核。
27. 用户可以自选本轮测试节点，至少支持按优先级、环境组、沙箱类型和具体测试用例选择；该能力属于正式工作流入口，不要求每轮执行全量测试。筛选组合、依赖补齐及计划版本规则在设计草案中展开，尚无可运行实现。
28. 用户要求基于既有三套源码审计为所有测试场景细化统一口径的测试用例节点；先设计节点，不恢复提前产生的脚本实现。
29. 创建完成不必强制执行命令：可以检查沙箱状态，或使用经源码核验的完成日志。API 返回、状态就绪、服务端耗时与命令完成要区分，命令验证可以在创建停表后或独立用例中执行。Kuasar `sandbox launch terminal` 已确认有成功结果及 duration，但内部起点不同于客户端请求起点。
30. 密度测试同步采集各角色节点及各类组件的 PSS、累计 CPU 时间、CPU 峰值等资源开销；记录实际拉起及最终存活数量，用同范围同窗口真实实例数计算平均沙箱开销，区分直接、共享摊销、增量及失败成本，不能用请求数作分母。
31. 底噪内存统计以 PSS 为基础并剔除 Guest OS，保留原始值及扣除证据。Guest OS 的精确边界和可靠分离方法尚待明确，不能擅自减配置内存或任意 Guest used 值。
32. 密度增加固定总创建请求数、不同并发度的对比，支持滑窗和分批间歇两种发压方式，均同步采集性能与资源并保留成功实例。滑窗完成一个补一个；分批待本批结束后等待指定间隔再发下一批。实际在途上限与请求总数、批大小和批间隔分别建模，最终真实存活数与最大容量不同。
33. 所有需求澄清、规格和设计文档以工作节点为粒度补齐可脚本化职责，说明模型／人工承担的部分及触发条件，绘制节点内部工作流；必须区分计划脚本化和真实实现／验证状态。
34. 密度创建过程中同步采集每秒成功创建数及吞吐，不只记录最终实例数；按所选创建完成判据计数，并与发起／接纳速率、失败／迟到、最终存活数分开。
35. 基于已澄清需求进入图编排代码详细设计及其工程测试设计，仍先设计后实现；设计方法采用 OpenSpec 承载产物，并以 brainstorming 检查完整性。技术提案与用户已确认条件分别标记。

36. Q3 已确认：旧任务按原图版本完成或清理，新计划使用新图版本并复用有效证据；不在活动图实例内热切换拓扑。激活、收尾与复用的协议及测试见代码设计 D14、ORC-056，实施清单见 `tasks.md`。

37. 用户要求同时交付用例执行代码设计、检验测试代码的契约测试设计及实施任务；覆盖三产品适配、基础场景、密度发压、资源采集和统计。执行设计见 `benchmark-design.md`，代码契约见 `benchmark-contract-design.md`，任务 15–27。用户随后授权设计审阅完成后继续 apply；真实测试条件缺失仍须保持明确阻塞。

### 设计基线与仍需细化的事项

自动化职责的完整逐节点清单见 [node-automation.md](node-automation.md)，内部图见 [node-workflows.md](node-workflows.md)。脚本负责确定性执行、状态转换、计数、计算、证据和规则校验；模型负责新语义／未知异常和报告解释；人工只解决未确定意图／目标／范围。五阶段全部有脚本化部分，分析和报告也不交给模型手工算数。现有草稿不计为已完成节点。

代码层的工程提案见 [orchestration-design.md](orchestration-design.md)，对应验证合同见 [orchestration-test-design.md](orchestration-test-design.md)。两者是现有 design 的附件；沿用 spec-driven schema，已有编排与脚本实现，生命周期增量已开始 apply，按任务逐项记录验证范围。Python/LangGraph、PostgreSQL、持久任务与事件 outbox 是本轮任务采用的工程设计基线，并非用户逐项指定的技术栈；更改基线须同步设计及验收。

- 优先评估 LangGraph 的主图、子图和持久化能力；LangChain 可用于模型和工具接入。
- 主图与子图显式传递必要信息，大型原始数据独立保存，状态只携带引用和摘要。
- 修改产生新工作流版本，按依赖和有效性复用旧证据；Q3 已确认新版本关联运行，旧任务原图收尾，不热切换拓扑。
- 建议使用版本化选择配置：同一维度多个值取并集、不同维度取交集，再应用排除；筛选优先级与执行排序分开。确定性脚本生成可预览计划，包含必要前置、有效证据复用和冲突说明，不把前置动作自动扩成其他场景的性能测试。具体优先级枚举、配置格式及选择界面尚未冻结。
- 场景节点草案见 `test-nodes.md`。建议创建默认比较客户端状态就绪，服务端日志耗时单列，功能后验与首次命令指标独立；具体完成合同、观察节奏与验证覆盖仍需冻结。底层官方方法作为参考分层，不与端到端时延直接混排。
- 建议使用可校验的环境声明文件及机器可读报告；`environment.yaml` 是候选文件名，字段行为已在 spec 中描述，具体序列化格式和完整 schema 未冻结。
- 环境检查发现差异，环境配置执行修改，修改后复检；该逻辑边界保留在五阶段流程中，不把安装动作隐藏为只读检查。
- 环境组边界已确认；组内工作 agent 的具体分配粒度按图工作节点继续细化，不按每台机器或每个测试请求无限扩张。
- 结论阶段继续脚本化事实表、图表、阈值判定、引用核对与归档；模型负责解释与建议，不预设模型使用比例。具体报告模板、工作簿分表及归档格式待细化。
